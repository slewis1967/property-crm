# Incident Post-Mortem — CRM "Internal Server Error" on login

| | |
|---|---|
| **Date** | 2026-05-23 → 2026-05-24 (AEST) |
| **Severity** | High — total loss of authenticated access to `crm.nextkey.com.au` |
| **Status** | Resolved (fix on branch `fix/crm-500-resilience`, pending squash-merge) |
| **Surface** | Next.js CRM, Netlify origin, behind Cloudflare Access |
| **Author** | Claude (diagnosis + fix); handover to Hermes (operator) |

## Summary
After passing the Cloudflare Access login gate, every request to the CRM returned a bare **HTTP 500 "Internal Server Error"**. The Next.js server was **failing to boot**: a startup environment validator (added in PR #9) threw on a required env var that, due to a name typo, could never be present. Two subsequent factors made it worse and harder to spot: a remediation PR (#10) that targeted the wrong layer and itself shipped broken, and a test that was written to the same wrong name and therefore masked the bug.

## Impact
- 100% of authenticated CRM pages returned 500. The app was unusable for all users.
- Duration: from the deploy of PR #9 until the fix merges. (Inbound email sync, NEXUS, and Supabase were unaffected — this was purely the web app failing to start.)

## Root cause
PR #9 (`c3b0480`, *"operational improvements — env validation, observability, tests"*) added `instrumentation.ts`, which Next.js runs **once at server startup**:

```ts
export async function register() {
  if (process.env.NEXT_RUNTIME === "nodejs") {
    const { validateEnv } = await import("./utils/validate-env");
    validateEnv();   // THROWS if any required var is missing
  }
}
```

`utils/validate-env.ts` listed:

```ts
{ name: "NEXUS_API_KEY", required: true, feature: "NEXUS API proxy" },
```

But the actual variable — used by `utils/nexus-api.ts` and present in `.env.local` / Netlify — is **`NEXUS_INTERNAL_API_KEY`**. `NEXUS_API_KEY` exists nowhere else in the codebase. So `validateEnv()` always counted it as missing, threw at boot, `register()` rejected, **the server never started, and every request 500'd** — including the login landing page.

Because the throw happens at **module load / server startup**, it is *above* any React error boundary or page-level `try/catch`. No amount of page hardening could catch it.

## Contributing factors
1. **Fail-fast taken too far.** `validateEnv` hard-throws at startup on *any* missing `required` var. This turned a one-character name typo into a complete outage. Backend-integration keys (NEXUS) were treated as boot-blockers.
2. **A test that encoded the bug.** `smoke.test.ts` set/checked `NEXUS_API_KEY` — the same wrong name — so the validator's test passed and gave false confidence that env validation was correct.
3. **Remediation aimed at the wrong layer.** PR #10 (`7dcf942`, *"add error boundary and harden home page data fetch"*) added a page-level `try/catch` + an error boundary. But a startup/module-load throw cannot be caught there, so it did not fix the outage.
4. **The remediation shipped broken.** PR #10's `app/page.tsx` contained malformed JSX (5 `<td className="…>` attributes missing their closing quote) and type errors, and its `app/error.tsx` destructured `resetError` while Next.js passes `reset` (so the "Try again" button called `undefined()`). A non-compiling landing page reached `master` — which implies the Netlify deploy-preview check either was not gating or was bypassed.
5. **A second latent total-outage trigger.** `utils/supabase.ts` also threw at module load if its env vars were unset. Imported by the root layout and nearly every route, a single missing Supabase var would have produced the identical symptom independently.

## Detection
Reported by the operator via the CRM login flow ("Internal Server Error"). There was no automated alert for the web app failing to boot — see action items.

## What went well
- Once the layered symptoms were peeled back, the root cause (a single wrong var name) was unambiguous and cheap to fix.
- The defense-in-depth changes mean a *future* missing env var degrades the relevant feature instead of taking down the whole CRM.

## What went wrong
- A typo in a `required: true` entry caused a total outage.
- A broken, non-building remediation reached `master`.
- The test suite validated against the buggy name, hiding the defect.

## Action items
1. **Run `next build` before every merge.** `tsc` alone does not catch RSC-boundary errors, missing `"use client"`, or (in some configs) the full set of JSX issues. The deploy-preview check must actually gate merges — confirm branch protection is enforcing `netlify/crmnex/deploy-preview` and that it cannot be bypassed. *(Owner: Hermes)*
2. **Do not hard-throw at startup for backend-integration env vars.** Reserve fail-fast for genuinely core vars (Supabase, Anthropic); treat integration keys (NEXUS, Brevo, ClickSend, Google) as `required: false` and degrade. Consider catching in `instrumentation.ts` and logging loudly rather than crashing the process. *(Owner: Hermes)*
3. **Keep `validate-env` names in sync with reality.** Add a test (or lint) that asserts every var name listed in `validate-env.ts` is actually referenced as `process.env.<NAME>` somewhere in the codebase — that single check would have failed on `NEXUS_API_KEY`. *(Owner: Hermes)*
4. **Tests must reflect real usage, not the code under test's assumptions.** The smoke test was written to the validator's (wrong) name. Cross-check env-var tests against actual `process.env` references. *(Owner: Hermes)*
5. **Fix at the failing layer.** A page-level error boundary cannot catch a startup/module-load throw. Identify where an error originates before "hardening." *(Owner: Hermes)*
6. **Add a boot/health alert.** A simple uptime check on an unauthenticated health endpoint (or the Cloudflare Access login page resolving) would have flagged the outage before a user did. *(Owner: Hermes)*
